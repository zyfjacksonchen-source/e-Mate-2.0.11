# e-Mate development rules

Read `docs/target-contract.md` and the latest entry in `docs/development-log.md` before changing code. A change that contradicts the target contract is invalid even when it makes a local test pass.

## First development rule: use native DSH Creation Mode first

- Before consulting or changing DSH behavior, resolve `desktop/e-mate-desktop/base-contract.json` and the checked-in Harness/Desktop-reference gitlinks. Every native comparison, copied seam, test fixture, and compatibility claim must use that exact e-Mate Base-bound Harness version and commit (currently DSH `0.1.0-rc.7` at `e13ce9d953037a2f40d866d17f5a7e00cbc15d66`, Desktop reference `6074088f5b660206e404b3591fab51fb99c69add`). A floating branch, latest tag, different RC, or unpinned checkout is not native evidence for this repository.
- When startup, rendering, permissions, tools, plugins, sessions, or Desktop packaging fail, trace the affected path end to end and compare the same owner and lifecycle against those pinned DSH rc.7 and Desktop-reference commits before designing a fix. Restore or adapt the native contract at its existing seam; do not patch only the visible symptom, infer behavior from a newer RC, or introduce a parallel loader, transport, permission model, session path, or Desktop lifecycle. Record the compared files/behavior and any intentional bounded difference in the development log.
- For any behavior that can live in the DSH plugin plane, begin in the shipped rc.7 `cordis` preset (“创造模式”): load its `cordis-plugin-development` or `editing-cordis-compositions` skill, inspect the live Host/Client Services, Events, Tools, and Slots through `cordis_inspect_*`, then prove the smallest reversible Host/Client package with the native define/run/stop/undefine lifecycle before writing a permanent implementation. Do not guess a Harness seam from screenshots or add a parallel runtime path.
- Creation Mode is the development inner loop, not a release format or admission bypass. Its dynamic packages are process-memory experiments, disappear on restart, and must never be copied directly into a release. A successful experiment is reimplemented as the smallest ordinary repository Profile plugin, bound to the exact Base/Harness contract, and then passes its component tests, composition check, signed immutable artifact, atomic generation switch, renderer-health acknowledgement, and rollback gate.
- Preserve the complete DSH shipped preset root (`standard`, `code`, `minimal`, and `cordis`) exactly as the matching `deepseek-harness-desktop` base does. The e-Mate persona may shadow `standard` in a separate managed root; it must not replace or edit the shipped root. `cordis` is explicit opt-in and must never become the ordinary session default.
- Treat Creation Mode as shell-equivalent trust. It may inspect and temporarily extend an explicitly selected local development session, but it receives no release credentials, signing keys, Feed activation authority, or silent production enablement. If a change belongs to Electron lifecycle, native packaging/signing, updater trust, or another Base-only plane that Creation Mode cannot represent, record that reason and follow the pinned Desktop reference instead of fabricating a plugin.
- Every development-log slice for a plugin-plane change records the inspected native seam, the temporary experiment or the reason it was unnecessary, the permanent plugin that replaced it, and the narrow gate that proves no dynamic package or second path entered the release.

## Non-negotiable boundaries

- Keep the DeepSeek Harness core at the bounded target fork commit recorded in `docs/target-contract.md` (currently `e13ce9d953037a2f40d866d17f5a7e00cbc15d66`); add e-Mate behavior through profiles, plugins, client slots, or generated distribution assets.
- Keep the enterprise administration/control plane on an exact allowlist: (1) identity, account, agreement and authentication-lease management; (2) managed model/search route policy and bounded credential leases; and (3) append-only redacted audit and usage. It must not read, mutate, authorize, enable, disable, install, dispatch, execute, or publish local Tools, plugins/Skills, files, workspaces, sessions, memory, artifacts, Computer Use/CDP, schedules/jobs, share content, Profile/updater/release state, or external-connection grants/actions. Tool/Skill/job identifiers, states and counts may enter only the redacted audit ledger and never become commands. Model requests may carry caller-owned Tool schemas and return model-selected Tool calls, but the enterprise plane never executes or dispatches them; local Harness remains the sole execution owner. Skill Hub and Share are separate user-initiated product data services, not administrator/control-plane powers, and their receipts grant no local mutation authority.
- The enterprise management UI may invoke only a manually initiated bounded connectivity probe through the existing authenticated same-origin Model Gateway session: catalog lookup plus one minimal text Responses request or capability-selected image generation. It must not receive upstream keys, accept arbitrary prompts, attach Tool schemas, call local Harness, persist generated content, or create a second provider/transport; quota enforcement and redacted usage audit remain mandatory.
- Render only real Harness events and plugin presentation metadata. Do not create fake activity events or hardcode tool names in the central chat UI.
- Preserve the model mapping and image-model fallback recorded in the target contract.
- Treat old e-Mate/ECoreX databases as read-only sources. Never resurrect cache-only deleted conversations.
- Missing credentials, test accounts, platform artifacts, or upstream packages are blockers. Do not replace them with approximate behavior or weaken acceptance.
- Reuse the `anywhere-labs/deepseek-harness-desktop` Electron/Cordis packaging and lifecycle. Desktop-only adapters such as formal packaging and auto-update belong in `desktop/e-mate-desktop`; do not add another desktop shell, Host, session transport, Agent loop, or updater protocol.

## Desktop startup contract

- The accepted e-Mate 2.0.11 commit `6a7f4b9d59a1d8970345638946fb6564e2f5f93e` and its installed artifact define the predecessor's native Desktop startup flow: the packaged Electron process becomes ready, restores the bounded shell environment, resolves the receipt-governed local Profile, boots the in-process Cordis Host, mounts the loopback Web surface in the native BrowserWindow, and commits only on renderer health. Optional work such as CDP Chrome, update/network checks, cleanup, Skills, and capability maintenance starts on first use or after the interactive surface; later versions must preserve this one lifecycle and may not add a launcher service, CLI Host subprocess, external browser carrier, or parallel startup path.
- macOS and Windows must keep the same upstream startup order: packaged Electron becomes ready, resolves the fixed local profile, boots the in-process Cordis Host, loads its loopback Web surface, and shows the native window. Do not replace this with a launcher service, CLI subprocess, external browser carrier, or parallel local server.
- A warm launch must never copy, install, hash the full tree of, or mutate the managed profile. The managed profile may be repaired only when its versioned installation receipt or a narrow critical-file check fails. Windows command shims may be atomically refreshed, but must not execute pnpm or DSH during application startup.
- Keep network requests, update checks/downloads, obsolete-install cleanup, CDP endpoint checks, Accessibility setup, Skill installation, and other optional maintenance outside the first-interactive-window critical path. Failures in those tasks must not delay or blank the local shell.
- Measure startup from launching the installed application to a visible, AX-readable, clickable Harness surface. Measure renderer health separately; do not use a process-alive check, a loading screen, or direct execution from a compressed DMG as an interactive-start proxy.
- The accepted installed e-Mate 2.0.11 artifact is the startup-performance baseline; there is no standalone 15-second ceiling. Measure the candidate and 2.0.11 with the same machine, architecture, install/copy state, authentication state, profile state, launch command, probe boundary, and sampling order. When identity is required, the visible, AX-readable, clickable login form is the interactive surface. The AURA renderer must remain statically bundled and eagerly mounted with that route, with no dynamic import, runtime CDN, or login-time asset download; WebGL initialization may not delay or disable the form.
- Every release candidate must use the exact immutable artifacts intended for publication. On release hardware, run one clean installed launch and three sequential warm launches for both 2.0.11 and the candidate per applicable platform. For the clean sample, warm p75, and warm maximum, `candidate - paired 2.0.11 baseline` must be at most 10,000 ms. Discard only a complete baseline/candidate pair affected by documented machine interference, then rerun that pair. Record all raw timings, artifact identities, and conditions in `docs/development-log.md`; a regression outside this tolerance or missing paired evidence blocks release.
- The release gate must also prove macOS arm64 reaches the interactive Harness shell, x86_64/Rosetta reaches Electron native readiness with the complete x86_64 inventory, and Windows x64 reaches renderer health. Rosetta is a compatibility probe, not an Intel startup-performance proxy; native Intel performance evidence must run on Intel hardware when required. Architecture health cannot substitute for the paired 2.0.11 startup comparison above.

## Incremental release contract

- Natural-language update remains a first-class Agent operation. “检查更新”, “更新插件”, and “更新 e-Mate” must route through the one typed `e_mate_desktop_update` Tool and the existing native Desktop update service; never synthesize npm/pnpm/CLI commands, add a keyword matcher, or create a second updater. The explicit user request authorizes the signed metadata check; the native confirmation must show release version, changed components, compatibility, and remaining bytes before any component payload is downloaded and before restart is scheduled.
- Update selection is component-first and Base-fallback. A compatible signed Profile generation downloads only missing content-addressed components, is rechecked after confirmation, stages atomically, restarts, and commits only on Renderer health. `base-required` must trigger the existing Base-release check; if no compatible Base is published, report the block without staging either path.
- The one repository change-impact classifier is the authority for CI, test, and release lanes. Unknown paths, malformed input, unavailable merge bases, or incomplete component metadata fail closed to `base`; do not duplicate its path rules in workflow YAML.
- `plugin-only` is a proved property, not a label. It is valid only for independently packaged official Profile components whose exact base/Harness compatibility and production inputs are unchanged outside those component roots. A plugin-only job must emit evidence that Desktop, Harness, shared Profile, locks, packaging, updater, native helpers, permissions, and third-party state were untouched.
- 定时任务同样遵守“一切皆插件”：管理投影必须由 `@e-mate/dsh-plugin-schedules` 热组件提供，管理页只把用户带回原生会话调用 rc.7 `schedule_create`、`schedule_list`、`schedule_delete`；只可从原生 `create/delete/dispatch` 事件投影 `scheduled/overdue`、一次性 `completed` 和最近执行，不得伪造 rc.7 没有的 pause/resume/edit/run-now。不得把调度逻辑写回 Desktop/Base，也不得新增任务表、历史库、计时器、执行器或第二事件链。修改该能力时，必须同时通过组件 Lane、原生 Schedule 全套测试、Tool Search 共存测试和安装态创建/读取/删除验收。
- 真实用户逃逸缺陷按证据层修复，不按截图逐处打补丁：先在精确候选回放并写出唯一 Owner 与用户可见不可变式，再在首次能观察该不可变式的最低层补失败测试；随后依次验证 clean emitted `lib`、完整 generation、实际安装/在线增量更新、真实账号或上游、跨会话/重启/失败回滚中本次变更涉及的层级。只验证函数调用、源码字符串、Mock 凭据或旧 App 不能作为完成证据；修复必须复用锁定 rc.7/Desktop reference 的原生路由、存储、Tool、凭据和事件 Owner，不得新增平行实现。
- A plugin incompatible with the installed base is never installed speculatively. Select a compatible Base release first; if no signed compatible base exists, block the update. Compatibility is an explicit allowlist of tested contract ids, never `>=`, caret, tag, rc-name, or other SemVer inference.
- Official updates stage a complete Profile generation, preserve the third-party overlay, switch atomically on a separately confirmed restart, and commit only after the existing renderer-health acknowledgement. Keep the 2.0.10 Desktop installer/update path and native platform gates intact for Base releases.
- Determine the affected release stages from the actual diff before dispatching CI. Reuse an already accepted immutable artifact when its product inputs are unchanged; a test, documentation, release-verifier, or single-platform change must not trigger unrelated platform or carrier rebuilds.
- Rerun only the failed or affected stage. A full cross-platform rebuild is allowed only when shared runtime code, the managed profile, bundled dependencies, lockfiles, packaging inputs, or artifact provenance changed, or when existing evidence cannot prove the artifact is unchanged and accepted.
- Reused artifacts must keep their original commit, workflow run, byte count, and SHA-256 provenance. Release workflows must verify that provenance before composition and must never relabel old bytes as a newer commit. Feed or `latest.json` activation remains the final atomic step after every selected artifact passes its own gate.

## Fixed version iteration protocol

- Start every version from the exact accepted predecessor commit and public release receipts, never from a dirty worktree, a floating branch, or whatever package happens to be installed locally. Before implementation, record the version, source SHA, Base contract id, Harness and Desktop-reference pins, accepted component inventory, current three-target desired-state generations, and installer manifest.
- Resolve the current e-Mate Base-bound DSH/Harness/Desktop references before comparing with "native DSH". A newer tag or RC is research input only until the repository Base contract deliberately adopts it; it must not silently redefine the baseline during a version.
- Give every change exactly one owner before editing: pinned DSH core, one admitted Profile component, Desktop Base, or enterprise control plane. Reuse the native owner and contract. Do not move shared behavior into Base merely to make a plugin easier, and do not create a second renderer, registry, transport, updater, permission store, credential store, or session model.
- Prefer the plugin plane. A change may enter the Base lane only when it changes the shared ABI/runtime, Desktop lifecycle, packaging, updater trust, native helper, Base-owned roster, or another input that an already installed Base cannot safely load. Changing a component inventory or retiring a Base-bundled package is a Base change; changing an already admitted compatible component is not.
- Hiding is not retiring. Hiding a product control must preserve the underlying DSH capability and its one native owner. Retirement must remove the package from the inventory, loader, packaged closure, dependency/patch/license records, and managed runtime through an explicit migration, with both positive replacement and negative absence tests.
- The actual installed production application is the runtime truth. Source, a stale generated `lib`, a development server, an unpacked preview, or an isolated Slot fixture may diagnose a bug but cannot prove that the shipped user path is fixed.

## Fast development loop

1. Resolve the fixed Base/DSH/Desktop pins, name the owning component, and run the one change-impact classifier against the candidate paths before building anything.
2. Reproduce the real user path. If the native seam is unknown, use rc.7 Creation Mode to inspect and prove it; if the seam is already directly proved by the pinned runtime, record why another dynamic experiment is unnecessary.
3. Add the smallest regression that fails for the root cause, fix the existing shared owner once, then run that regression and the owning component check. Avoid wrapper fixes, sibling patches, duplicate UI owners, and unrelated cleanup.
4. For release-affecting component work, compose the complete accepted generation for every affected target and boot the applicable final graph. Then stop. Do not run signing, installers, R2 publication, website deployment, or full carrier validation during ordinary development.
5. Target a focused regression at no more than 60 seconds, an affected-subsystem check at no more than 5 minutes, and development CI at no more than 10 minutes. Record a concrete reason when a gate exceeds its budget. Batch coherent accepted fixes before freezing a release; never use the installer pipeline as a daily debugger.
6. Run the smallest non-overlapping gate that proves the diff. A passed gate is not rerun unless its code, inputs, configuration, artifact bytes, or environment changed. A failed immutable candidate SHA is permanently invalid; rebuild only the affected stage and issue a new candidate.

## Release lanes and immutable publication

- The classifier decides the lane from the exact diff and fails unknown or mixed ownership closed to `base`. Workflow path lists, release scripts, and operators must consume its result rather than maintain another classifier.
- `docs-only`, `verification-only`, and `enterprise-only` produce no Desktop or Profile bytes. Component test-only changes run their relevant gates but publish nothing.
- A `plugin-only` release must not build Base, DMG, EXE, or unchanged components. It builds only the admitted changed components, preserves the exact accepted references for every unchanged component, and composes a complete signed generation for darwin-arm64, darwin-x64, and win32-x64. A target-bound component must run its native target job and complete-generation boot for every target.
- A `base` release is reserved for shared runtime/ABI, Base contract or inventory, DSH/Desktop reference, Desktop lifecycle, dependency or lock, packaging/updater/signing format, native helper, permissions integration, or other Base-owned inputs. Invalid contracts, blocked components, unowned paths, and incomplete provenance also fail closed to `base`.
- A protected PR artifact may be reused only when its exact tested tree equals the protected main tree and its commit, workflow run, bytes, manifest, and SHA-256 remain attributable. Actions cache is never release evidence; cross-workflow publication consumes an exact run artifact selected by run id and source SHA, then revalidates its manifest and bytes.
- `profile-release.yml` success means **publication prepared**, not online. It may validate an admitted CI run, sign the release, and emit a publication plan; it must not be reported as released until the R2 and installed-product gates below pass.
- Publish one immutable plan in this order: validate exact provenance/Base/targets/changed set/sequence; read all current pointers and match `expected_current`; upload only missing content-addressed component bytes and signed envelopes; reject an existing key unless its size and SHA-256 are identical; read every object back through the public endpoint and verify exact bytes; reread every pointer; then CAS-activate stable pointers last with `Cache-Control: no-store`.
- Three target pointers are not one transaction. On interruption, resume the same signed plan idempotently: an already activated target must be byte-for-byte the same candidate, and an untouched target must still match `expected_current`. Never mint a new sequence, overwrite a different parent, or hide partial activation.
- Validate a real delta from the immediately preceding production generation with candidate component bytes absent from cache. Trigger the sole typed updater with natural language, inspect the Chinese confirmation before download, verify the exact changed components/compatibility/remaining bytes, confirm, restart atomically, and require Renderer health, cleared pending state, `active = last_known_good = candidate`, and `previous_known_good = parent`. A first bootstrap from `bundled` is a full-generation cost and must never be reported as the normal plugin delta.
- A Base freeze runs the carrier loop once: exact source/contract, both platform package gates, all target-bound components against the new Base, then the one formal macOS universal DMG, Windows x64 EXE, and manifest. Test these exact bytes; do not rebuild after acceptance. Publish immutable installers and verify public full hashes before activating `desktop/latest.json`, bootstrap one complete compatible Profile generation from the accepted Base SDK artifact, and switch the website only after both planes are healthy.
- `mac-smoke` is CI-only and must never appear in a release manifest, R2, the download page, or user instructions. The website is a separate atomic, rollback-capable publication surface: preserve unrelated site content, switch a versioned relative symlink, and verify the live page, diagrams, installer links, content types, sizes, and full SHA-256 values in a real browser and by direct HTTP.
- Full Access is only the DSH filesystem/sandbox domain. It does not grant plugin resources, approval consent, macOS TCC, Computer Use, CDP, provider credentials, Skill installation, or MCP mutation. Each authority is validated at its own boundary, and `approval: never` fails a consent-requiring operation closed instead of silently approving it.
- Browser navigation and page actions use the native CDP plugin first. Computer Use is activated only by an explicit current-turn `@电脑操控` request and must not become a browser fallback. External provider credentials and grants are device/account state: verify and reuse them across sessions instead of projecting per-session bootstrap instructions that repeatedly log in.

## 2.0.11 failure ledger: permanent rules

- **Source tree is not the packaged product.** `registry.json`, dotfiles such as `.manifest.json`, nested `node_modules`, native prebuilds, architecture slices, and generated registries must be verified in the physical `afterPack` tree. `package:dir` and the formal carrier use the same runtime preparation path, and the Host/Profile/Client Loader plus required imports/helpers are smoked from those final bytes.
- **The CLI dependency tree is not the Desktop dependency tree.** A pnpm Harness patch does not prove Electron Builder's Yarn graph changed. Runtime behavior tests execute the final Desktop dependency bytes, and product Node/Python runtimes come only from the fixed Base; CI setup runtimes are build tools, never product authority.
- **One inventory and one visible owner.** The accepted component inventory drives composition, loading, packaging, publishing, and retirement. Each control, renderer, and state transition has one Slot/service/store owner. Native Agent messages stream outside the single collapsed running-process group; Think/Reasoning, Tool, Bash, and Context stay inside it; GenUI and native tool views remain delegated and compatible.
- **Session logs are a downstream compatibility boundary.** Every non-surface downstream event is written with explicit `ignorable: true`. Legacy recovery may recognize only an exact reviewed event allowlist; all other unknown events continue to fail closed. Acceptance includes write, exit, cold read, and an unknown-event negative test against the final Desktop graph; existing user logs are never rewritten in place.
- **Permissions are separate domains.** DSH sandbox, approval policy, plugin resource grants, OS TCC/helper identity, and credentials/Skill/MCP persistence neither imply nor overwrite one another. Computer Use acceptance requires the real packaged helper through authorize, restart/update, health, observe, and action; a UI label or process-alive check is insufficient.
- **External capability is end-to-end or unavailable.** A configured-looking button is not a working service. Sharing must prove create, restart/reload, public download, revoke, and 404/410; Skill Hub must prove publish, search, detail, install/enable, cross-session use, upload/delete, and permission boundaries. Unconfigured production services are shown as unavailable, not as successful local mocks.
- **Cross-Base selection happens before bootstrap validation.** Verify the signed public current release and target first, then select compatibility. Only an explicit `base-required` result permits a parentless complete bootstrap for the new Base; an already compatible current release rejects duplicate bootstrap.
- **Generated and cached state can be stale.** Cold CI must install every gate dependency explicitly. Generated bundles, profile projections, browser caches, Actions caches, and old website assets never override source and exact artifact provenance; verify the consumer-facing bytes after deployment.
- **Acceptance oracles do not own product defaults.** Executable smokes derive expected mode, graph, URL, version, and capability state from the same resolved owner contract as the product; they do not copy old literals. Every stateful smoke uses an isolated temporary `DSH_HOME`, is safe to run twice, and never reads or writes the operator's real sessions. When an owner default or composition changes, search its direct smokes and user-facing documentation for the retired value before freezing the candidate.
- **Performance claims need paired evidence.** TTFT and tok/s samples from one run are diagnostics, not parity proof. Compare the same model, prompt, network route, tools, warm/cold state, and production build against the accepted baseline before claiming no regression.
- **A release record names the exact truth stage.** Use only `source fixed`, `candidate built`, `installed accepted`, and `production released`. CI green, a signed plan, an uploaded subset, or a source screenshot must not be described as online. Missing platform evidence remains explicitly unverified.

## Definition of done

- `source fixed`: the root-cause regression and owning-component checks pass on the exact source SHA.
- `candidate built`: complete required artifacts/generations exist with exact run id, source SHA, byte count, manifest, and SHA-256 provenance; no production pointer changed.
- `installed accepted`: those exact immutable bytes pass the affected real installed user paths, permissions, restart, history cold-read, rendering, state, rollback, and measured-performance gates required by the lane.
- `production released`: every immutable public object and stable pointer was read back and verified, the previous production install completed the natural-language atomic update, and the live download surface was checked when affected. Only this stage may be called "released" or "online".

## Work loop

1. Name the active slice in the development log.
2. Record newly verified facts before changing the implementation when they affect the architecture or release path.
3. Implement the smallest end-to-end path for the slice.
4. Run the narrowest test that proves the path, then its composition check.
5. Record commands, outcomes, remaining gaps, and the next slice.

The main agent owns acceptance. A child agent may repair one documented failure, but the main agent must rerun the failed scenario before closing it.
