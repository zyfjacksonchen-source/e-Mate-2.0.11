# e-Mate development rules

Read `docs/target-contract.md` and the latest entry in `docs/development-log.md` before changing code. A change that contradicts the target contract is invalid even when it makes a local test pass.

## Authoritative local test, build, and release flow

This section overrides every later rule that requires GitHub Actions, protected-main CI, or CI artifacts. Until the user explicitly changes the project flow again, e-Mate is tested, built, verified, published, and rolled back locally through the repository's single `corepack pnpm flow` owner. This is the only recommended operator entry: do not invoke a cached `pnpm.cjs`, a bare fallback pnpm, `scripts/local-flow.mjs` directly, or GitHub CI. Corepack must resolve the root `packageManager` exactly (`pnpm@11.7.0`); a machine without that pinned entry stops before creating a run.

On macOS, Corepack itself must run under a standalone Node distribution that can load third-party native addons. An application-bundled Corepack wrapper that forcibly re-enters its application-bundled Node is not an admissible carrier, even when its Node version and ABI match. If Corepack is available only inside an application bundle, invoke that bundle's Corepack JavaScript entry directly with the accepted standalone Node; do not invoke the bundle's wrapper. Before any `flow` run is created, verify under that same carrier that `process.execPath` is the intended standalone Node, Corepack starts, Corepack resolves the root pin as `pnpm@11.7.0`, and a platform-matched third-party native addon from the already-materialized dependency closure can actually be loaded. A missing closure or failed native-addon probe stops before the run; do not skip install scripts, rebuild around library validation, or install a second package manager/toolchain to hide the carrier error.

The inherited pinned pnpm JavaScript entry is also the authority for child package lifecycles; it is not assumed to exist as a bare PATH command. Before a run or platform build proceeds, local flow creates one temporary run-scoped `pnpm` carrier for that exact entry and standalone Node, prepends it to every child environment, verifies nested command resolution, rejects version or byte drift, and removes it in `finally` on macOS and Windows. Do not patch individual package scripts, install a global pnpm, or retain the carrier after the flow. This is build-tool plumbing only; installer download, Profile objects, online update, rollback, and activation remain canonical Cloudflare R2 data-plane operations exclusively.

Desktop packaging also requires Electron Builder's npm collector carrier. Before creating a candidate run, the flow must resolve an already-installed standard `npm/bin/npm-cli.js` from the accepted Node/Corepack distribution, execute it with that same standalone `process.execPath`, and prove the exact Electron Builder `npm list` command returns a JSON dependency tree. An application wrapper that forces its bundled Node, an unrelated PATH npm, or a differently distributed Windows `npm.cmd` is not admissible. On macOS, only the Desktop child stages receive a run-scoped temporary `npm`/`node` shim and the flow removes it in `finally`; Windows retains its native `npm.cmd` only when it is colocated with the active Node. A missing or mismatched carrier stops before the run; do not install npm, change the lock or builder, or skip collection. This is a local build-tool input only: client installer download, online update, and rollback continue to use Cloudflare R2 exclusively.

For the current 2.0.15 closeout, replacement acceptance starts from a real installed 2.0.13 predecessor obtained through the official Cloudflare R2 manual-download path; future online-update acceptance starts from an already installed 2.0.15 and covers only a strictly higher SemVer successor such as 2.0.16+. The Settings action uses the existing native bridge; Agent natural language uses the one typed `e_mate_desktop_update` Tool; both converge on the same `desktopUpdates.runInteractiveUpdate` service. That service fetches the real signed schema-2 manifest and installer from canonical Cloudflare R2, downloads the selected bytes, then revalidates the landed bytes/size/SHA-256, Windows PE shape, and signed manifest identity before installer handoff. On Windows it starts the pinned Desktop-reference standard assisted NSIS Setup with exactly `--updated --force-run` and requests orderly application shutdown only after the child reports successful spawn. It does not use `/S`, a private request/token, a candidate directory, journal, ACK, or custom health rollback. The exact installer bytes already passed installed acceptance, so this focused future gate does not repeat replacement or relaunch; 2.0.13 and same-version 2.0.15 migration remain manual-download cases, never alternate feeds or same-version online updates.

Every native Base update preserves one visible installed application. macOS atomically replaces canonical `/Applications/e-Mate.app` and continues using the same bundle path for Dock and LaunchServices; its predecessor may exist only as a transaction-internal rollback backup while health and commit are unresolved, and successful commit deletes that backup. Windows build and replacement acceptance use only SSH alias `win-test-server` on actual host `172_16_48_13`: the request-bound 2.0.15 EXE built there must use the pinned Desktop-reference standard assisted NSIS path to replace that host's existing directory `C:\Users\Administrator\AppData\Local\Programs\e-Mate` in place, and the sole Desktop and Start Menu shortcuts must both resolve to that same directory's `e-Mate.exe` before and after replacement. Its exact-process graceful shutdown and scoped process fallback are existing reference behavior, not a new updater, transaction, or fallback installation path; Windows has no custom candidate tree or health-rollback owner. Never leave a second `.app`, installation directory, Desktop shortcut, or Start Menu shortcut.

1. During development, run the narrow owning check or `corepack pnpm flow dev`. Keep the main acceptance sweep running, record all failures, and route them directly to dedicated subagents; do not create user-visible Codex Threads for further 2.0.15 work. Each subagent still owns exactly one ticket, branch, worktree, and commit, while T00 only coordinates, reviews, corrects, merges, and judges evidence. Do not rebuild an installer after each defect; batch the accepted fixes first.
2. Freeze one exact committed, clean source SHA, then run `corepack pnpm flow candidate` exactly once. It performs the deterministic source/component gates before Desktop packaging, builds the unsigned macOS installer, and emits the exact Windows build request only after verified macOS candidate bytes exist. A toolchain, source, component ABI, or packaging failure keeps Windows blocked and emits no usable request.
3. Keep the accepted macOS bytes and product source SHA immutable. A later clean release-control checkout may reissue only the Windows request by proving it is a closed control-plane descendant and passing `--product-source` to a separate committed-clean checkout at the exact frozen product SHA; the internal command then invokes the existing `platformBuild` exactly once against that product checkout. Carry that request only through SSH alias `win-test-server`, whose actual hostname must be `172_16_48_13`, and import its result without rebuilding macOS. The existing protected-main `.github/workflows/ci.yml` `workflow_dispatch` release-candidate owner is the only permitted fallback builder, but it necessarily rebuilds both platforms and cannot fill this frozen mixed-source run; if the test server cannot build, keep this run open unless a new full candidate is explicitly authorized. Do not create another Workflow or builder, select another Windows host or transport, or substitute a later product SHA. Windows Computer Use remains `ALLOWED_UNAVAILABLE / NOT_APPLICABLE` independently of the build route.
4. Run `corepack pnpm flow verify --run <run-id>` against the exact candidate bytes. The normal path still requires both platforms; the explicit Windows-unavailable path may close only as `passed-macos-only`, with Windows remaining unverified. Windows installed acceptance is accepted only from SSH alias `win-test-server` with actual host `172_16_48_13`; it must prove the real installed 2.0.13 predecessor version, application path and both shortcut targets, then prove exact-candidate 2.0.15 replacement reused that same directory, both final shortcuts resolve to its `e-Mate.exe`, startup is healthy, and exactly one application remains. A future `new-version` transaction closes only after a real signed strictly higher manifest and installer exist on canonical Cloudflare R2 and the installed 2.0.15 native updater proves download, landed bytes/size/SHA-256/platform format, and pre/post signed-manifest identity. 2.0.13 and same-version migration remain manual downloads; full-product, rollback, built-in Tool, and Computer Use retesting are not part of this focused release gate.
5. Run `corepack pnpm flow publish --run <run-id>` to emit the bounded first-stage request for the existing Cloudflare Owner. For a full release, that stage may only create source-scoped immutable installer keys (or accept already-exact bytes) and must complete authenticated and public full-byte readback before `--owner-receipt` can advance the run. The protected-main attempt-1 carrier is only the existing candidate-provenance bridge: it downloads the exact receipt-bound installers from canonical R2, verifies bytes and hashes, materializes exactly `desktop-candidate.json` plus DMG plus EXE with the real workflow run id, and uploads that three-file artifact for the external schema-2 signer. It never builds installers, writes R2, switches pointers, serves downloads, or becomes ordinary CI. After the exact carrier receipt, local flow advances through `awaiting-signing-input-owner → awaiting-protected-signer → awaiting-activation-owner`; the protected signer hydrates the already-published installers, uses the pinned external schema-2/no-performance/single-provenance signer, then must extract and execute the actual bundled update Reader against the final signed manifest. A current same-version 2.0.15 replacement must return `up-to-date`; a future version must use the exact public 2.0.15+ predecessor Reader and return `update-available`. Local import requires the compact result and a separate GitHub-API Owner receipt. Version freeze binds all stages to one transaction: publish or replace the versioned manual manifest, CAS only `desktop/signed/latest.json`, and leave `desktop/latest.json` unchanged as the pre-2.0.15 bootstrap/manual-migration surface; rollback reverses only the writes actually made. Real 2.0.13 and existing same-version old 2.0.15 installations use the official Cloudflare R2 manual download page. No second feed, updater, publisher, fabricated performance admission, rebuilt accepted bytes, GitHub client URL, or legacy-pointer activation is allowed.
6. Every produced installer is intentionally unsigned for this release. Keep credentials redacted and preserve exact source/candidate/installed/public truth boundaries. If a local-flow capability is missing, repair that single owner or stop with the exact gap; never substitute CI, an unrecorded transport, a second publisher, or a parallel build path.

## First development rule: use native DSH Creation Mode first

- Before consulting or changing DSH behavior, resolve `desktop/e-mate-desktop/base-contract.json` and the checked-in Harness/Desktop-reference gitlinks. Every native comparison, copied seam, test fixture, and compatibility claim must use that exact e-Mate Base-bound Harness version and commit (currently DSH `0.1.0-rc.7` at `32728743c28911bcd4279f79fe9c43ee7aacfb6d`, Desktop reference `6074088f5b660206e404b3591fab51fb99c69add`). A floating branch, latest tag, different RC, or unpinned checkout is not native evidence for this repository.
- When startup, rendering, permissions, tools, plugins, sessions, or Desktop packaging fail, trace the affected path end to end and compare the same owner and lifecycle against those pinned DSH rc.7 and Desktop-reference commits before designing a fix. Restore or adapt the native contract at its existing seam; do not patch only the visible symptom, infer behavior from a newer RC, or introduce a parallel loader, transport, permission model, session path, or Desktop lifecycle. Record the compared files/behavior and any intentional bounded difference in the development log.
- For any behavior that can live in the DSH plugin plane, the default development path is the shipped rc.7 `cordis` preset (“创造模式”): load its `cordis-plugin-development` or `editing-cordis-compositions` skill, inspect the live Host/Client Services, Events, Tools, and Slots through `cordis_inspect_*`, then send the smallest Codex-authored dynamic Host/Client package through the native define/run/stop/undefine and hot-replace lifecycle in the explicitly selected isolated local development session. After every change, exercise the narrow real interaction and owning regression there immediately before writing a permanent implementation. Do not guess a Harness seam from screenshots or add a parallel runtime path.
- Creation Mode is the development inner loop, not a release format or admission bypass. Its dynamic packages are process-memory experiments, disappear on restart, and must never be copied directly into a release. After each change is independently verified in place, batch coherent changes only at version freeze and reimplement each one in its existing owning ordinary repository Profile plugin, bound to the exact Base/Harness contract; the resulting generation then passes component tests, composition, signing, atomic activation, renderer-health and rollback gates.
- Preserve the complete DSH shipped preset root (`standard`, `code`, `minimal`, and `cordis`) exactly as the matching `deepseek-harness-desktop` base does. The e-Mate persona may shadow `standard` in a separate managed root; it must not replace or edit the shipped root. `cordis` is explicit opt-in and must never become the ordinary session default.
- Treat Creation Mode as shell-equivalent trust. It may inspect and temporarily extend an explicitly selected local development session, but it receives no signing, R2, Feed, production desired-state, release credential, or silent production enablement authority. Its in-place result is development evidence only and never replaces installed-state, cross-platform, rollback, or release acceptance. If a change belongs to Electron lifecycle, native packaging/signing, updater trust, or another Base-only plane that Creation Mode cannot represent, record that reason and follow the pinned Desktop reference lifecycle instead of fabricating a plugin.
- Every development-log slice for a plugin-plane change records the inspected native seam, the temporary experiment or the reason it was unnecessary, the permanent plugin that replaced it, and the narrow gate that proves no dynamic package or second path entered the release.

## Non-negotiable boundaries

- Keep the DeepSeek Harness core at the bounded target fork commit recorded in `docs/target-contract.md` (currently `32728743c28911bcd4279f79fe9c43ee7aacfb6d`); add e-Mate behavior through profiles, plugins, client slots, or generated distribution assets.
- Keep the enterprise administration/control plane on an exact allowlist: (1) identity, account, agreement and authentication-lease management; (2) managed model/search route policy and bounded credential leases; and (3) append-only redacted audit and usage. It must not read, mutate, authorize, enable, disable, install, dispatch, execute, or publish local Tools, plugins/Skills, files, workspaces, sessions, memory, artifacts, Computer Use/CDP, schedules/jobs, share content, Profile/updater/release state, or external-connection grants/actions. Tool/Skill/job identifiers, states and counts may enter only the redacted audit ledger and never become commands. Model requests may carry caller-owned Tool schemas and return model-selected Tool calls, but the enterprise plane never executes or dispatches them; local Harness remains the sole execution owner. Skill Hub and Share are separate user-initiated product data services, not administrator/control-plane powers, and their receipts grant no local mutation authority.
- The enterprise management UI may invoke only a manually initiated bounded connectivity probe through the existing authenticated same-origin Model Gateway session: catalog lookup plus one minimal text Responses request or capability-selected image generation. It must not receive upstream keys, accept arbitrary prompts, attach Tool schemas, call local Harness, persist generated content, or create a second provider/transport; quota enforcement and redacted usage audit remain mandatory.
- Render only real Harness events and plugin presentation metadata. Do not create fake activity events or hardcode tool names in the central chat UI.
- Preserve the model mapping and image-model fallback recorded in the target contract.
- Treat old e-Mate/ECoreX databases as read-only sources. Never resurrect cache-only deleted conversations.
- Missing credentials, test accounts, platform artifacts, or upstream packages are blockers. Do not replace them with approximate behavior or weaken acceptance.
- Reuse the `anywhere-labs/deepseek-harness-desktop` Electron/Cordis packaging and lifecycle. Desktop-only adapters such as formal packaging and auto-update belong in `desktop/e-mate-desktop`; do not add another desktop shell, Host, session transport, Agent loop, or updater protocol.

## Desktop startup contract

- The accepted e-Mate 2.0.11 commit `6a7f4b9d59a1d8970345638946fb6564e2f5f93e` and its installed artifact define the predecessor's native Desktop startup flow: the packaged Electron process becomes ready, restores the bounded shell environment, resolves the receipt-governed local Profile, boots the in-process Cordis Host, mounts the loopback Web surface in the native BrowserWindow, and commits only on renderer health. Optional work such as CDP Chrome, update/network checks, cleanup, Skills, and capability maintenance starts on first use or after the interactive surface; later versions must preserve this one lifecycle and may not add a launcher service, CLI Host subprocess, external browser carrier, or parallel startup path.
- macOS and Windows must keep the same upstream startup order: packaged Electron becomes ready, resolves the fixed local profile, boots the in-process Cordis Host, loads its loopback Web surface, and shows the native window. Do not replace this with a launcher service, CLI subprocess, external browser carrier, or parallel local server.
- A warm launch must never copy, install, hash the full tree of, or mutate the managed profile. The managed profile may be repaired only when its versioned installation receipt or a narrow critical-file check fails. Windows command shims may be atomically refreshed, but must not execute pnpm or DSH during application startup.
- Keep network requests, update checks/downloads, obsolete-install cleanup, CDP endpoint checks, Accessibility setup, Skill installation, and other optional maintenance outside the first-interactive-window critical path. Failures in those tasks must not delay or blank the local shell.
- Measure startup from launching the installed application to a visible, AX-readable, clickable Harness surface. Measure renderer health separately; do not use a process-alive check, a loading screen, or direct execution from a compressed DMG as an interactive-start proxy.
- The accepted installed e-Mate 2.0.11 artifact is the startup-performance baseline; there is no standalone 15-second ceiling. Measure the candidate and 2.0.11 with the same machine, architecture, install/copy state, authentication state, profile state, launch command, probe boundary, and sampling order. When identity is required, the visible, AX-readable, clickable login form is the interactive surface. The AURA renderer must remain statically bundled and eagerly mounted with that route, with no dynamic import, runtime CDN, or login-time asset download; WebGL initialization may not delay or disable the form.
- Startup timing remains an optional diagnostic over the exact immutable artifacts intended for publication. When run, compare one clean and three warm launches against the accepted predecessor under the same conditions and record raw timings without relabelling or inventing samples. Missing or out-of-budget timing evidence does not block Desktop/Profile admission, signing, publication, or rollback.
- The release correctness gate still proves macOS arm64 reaches the interactive Harness shell, x86_64/Rosetta reaches Electron native readiness with the complete x86_64 inventory, and Windows x64 reaches renderer health. Rosetta is a compatibility probe, not an Intel performance proxy.

## Incremental release contract

- Natural-language update remains a first-class Agent operation. “检查更新”, “更新插件”, and “更新 e-Mate” must route through the one typed `e_mate_desktop_update` Tool and the existing native Desktop update service; never synthesize npm/pnpm/CLI commands, add a keyword matcher, or create a second updater. The explicit user request authorizes the signed metadata check; the native confirmation must show release version, changed components, compatibility, and remaining bytes before any component payload is downloaded and before restart is scheduled.
- Update selection is component-first and Base-fallback. A compatible signed Profile generation downloads only missing content-addressed components, is rechecked after confirmation, stages atomically, restarts, and commits only on Renderer health. `base-required` must trigger the existing Base-release check; if no compatible Base is published, report the block without staging either path.
- The one repository change-impact classifier is the authority for CI, test, and release lanes. Unknown paths, malformed input, unavailable merge bases, or incomplete component metadata fail closed to `base`; do not duplicate its path rules in workflow YAML.
- `plugin-only` is a proved property, not a label. It is valid only for independently packaged official Profile components whose exact base/Harness compatibility and production inputs are unchanged outside those component roots. A plugin-only job must emit evidence that Desktop, Harness, shared Profile, locks, packaging, updater, native helpers, permissions, and third-party state were untouched.
- 定时任务同样遵守“一切皆插件”：管理投影必须由 `@e-mate/dsh-plugin-schedules` 热组件提供，管理页只把用户带回原生会话调用 rc.7 `schedule_create`、`schedule_list`、`schedule_delete`；只可从原生 `create/delete/dispatch` 事件投影 `scheduled/overdue`、一次性 `completed` 和最近执行，不得伪造 rc.7 没有的 pause/resume/edit/run-now。不得把调度逻辑写回 Desktop/Base，也不得新增任务表、历史库、计时器、执行器或第二事件链。修改该能力时，必须同时通过组件 Lane、原生 Schedule 全套测试、Tool Search 共存测试和安装态创建/读取/删除验收。
- 真实用户逃逸缺陷按证据层修复，不按截图逐处打补丁：先在精确候选回放并写出唯一 Owner 与用户可见不可变式，再在首次能观察该不可变式的最低层补失败测试；随后依次验证 clean emitted `lib`、完整 generation、实际安装/在线增量更新、真实账号或上游、跨会话/重启/失败回滚中本次变更涉及的层级。只验证函数调用、源码字符串、Mock 凭据或旧 App 不能作为完成证据；修复必须复用锁定 rc.7/Desktop reference 的原生路由、存储、Tool、凭据和事件 Owner，不得新增平行实现。
- A plugin incompatible with the installed base is never installed speculatively. Select a compatible Base release first; if no signed compatible base exists, block the update. Compatibility is an explicit allowlist of tested contract ids, never `>=`, caret, tag, rc-name, or other SemVer inference.
- Official updates stage a complete Profile generation, preserve the third-party overlay, switch atomically on a separately confirmed restart, and commit only after the existing renderer-health acknowledgement. Keep the 2.0.10 Desktop installer/update path and native platform gates intact for Base releases.
- Determine the affected release stages from the actual diff before dispatching CI. Reuse an already accepted immutable artifact when its product inputs are unchanged; a test, documentation, release-verifier, or single-platform change must not trigger unrelated platform or carrier rebuilds.
- Rerun only the failed or affected stage. A full cross-platform rebuild is allowed only when shared runtime code, the managed profile, bundled dependencies, lockfiles, packaging inputs, or artifact provenance changed, or when existing evidence cannot prove the artifact is unchanged and accepted.
- Reused artifacts must keep their original commit, workflow run, byte count, and SHA-256 provenance. Release workflows must verify that provenance before composition and must never relabel old bytes as a newer commit. Feed or `latest.json` activation remains the final atomic step after every selected artifact passes its own gate.

## Fixed version iteration protocol

- Start every version from the exact accepted predecessor commit and public release receipts, never from a dirty worktree, a floating branch, or whatever package happens to be installed locally. Before implementation, record the version, source SHA, Base contract id, Harness and Desktop-reference pins, accepted component inventory, current three-target desired-state generations, and installer manifest.
- Resolve the current e-Mate Base-bound DSH/Harness/Desktop references before comparing with "native DSH". A newer tag or RC is research input only until the repository Base contract deliberately adopts it; it must not silently redefine the baseline during a version.
- Give every change exactly one owner before editing: pinned DSH core, one admitted Profile component, Desktop Base, or enterprise control plane. Reuse the native owner and contract. Do not move shared behavior into Base merely to make a plugin easier, and do not create a second renderer, registry, transport, updater, permission store, credential store, or session model.
- Prefer the plugin plane. A change may enter the Base lane only when it changes the shared ABI/runtime, Desktop lifecycle, packaging, updater trust, native helper, Base-owned roster, or another input that an already installed Base cannot safely load. Changing a component inventory or retiring a Base-bundled package is a Base change; changing an already admitted compatible component is not.
- Hiding is not retiring. Hiding a product control must preserve the underlying DSH capability and its one native owner. Retirement must remove the package from the inventory, loader, packaged closure, dependency/patch/license records, and managed runtime through an explicit migration, with both positive replacement and negative absence tests.
- The actual installed production application is the runtime truth. Source, a stale generated `lib`, a development server, an unpacked preview, or an isolated Slot fixture may diagnose a bug but cannot prove that the shipped user path is fixed.

## Fast development loop

1. Resolve the fixed Base/DSH/Desktop pins, name the owning component, and run the one change-impact classifier against the candidate paths before building anything.
2. For every plugin-plane change, use rc.7 Creation Mode by default: define/run the smallest dynamic package in the isolated development session, exercise the real narrow user path, and use stop/undefine plus redefine/run for immediate hot replacement after each edit. Skip this only when the pinned seam is already directly proved, and record why; Base-only work instead follows the pinned Desktop lifecycle.
3. After the in-place path is proved, add the smallest regression that fails for the root cause and reimplement the same seam once in its existing owning ordinary Profile plugin; then run that regression and the owning component check. The dynamic package remains disposable and never becomes a second path. Avoid wrapper fixes, sibling patches, duplicate UI owners, and unrelated cleanup.
4. Batch coherent, individually verified plugin changes when freezing a version, then compose the complete accepted generation for every affected target and boot the applicable final graph. Then stop. Do not run signing, installers, R2 publication, website deployment, or full carrier validation during ordinary development.
5. Target a focused regression at no more than 60 seconds, an affected-subsystem check at no more than 5 minutes, and development CI at no more than 10 minutes. Record a concrete reason when a gate exceeds its budget. Batch coherent accepted fixes before freezing a release; never use the installer pipeline as a daily debugger.
6. Run the smallest non-overlapping gate that proves the diff. A passed gate is not rerun unless its code, inputs, configuration, artifact bytes, or environment changed. A failed immutable candidate SHA is permanently invalid; rebuild only the affected stage and issue a new candidate.

## CI and release efficiency contract

This section is the authority when an older workflow rule conflicts with it. The pipeline invariant is **Build once -> Verify many -> Sign the exact bytes -> Publish without rebuild**. Faster execution never permits weaker installed-byte, provenance, security, rollback, or publication gates. Performance collection is optional diagnostics and is not a release-admission stage.

- Keep the pull-request lane and the formal-release lane separate. A normal PR runs source/unit/contracts, enterprise checks, changed-component checks, and affected-platform app-directory/renderer/Profile smokes. DMG/NSIS distribution packaging runs only for protected-main release candidates, changed packaging/updater/signing inputs, or an explicitly protected release-candidate dispatch. The engineering targets for Base PRs are 8-12 minutes wall clock and 25-35 runner minutes; measure 10-20 runs before converting any target into a hard gate.
- `scripts/change-impact.mjs` remains the only impact authority. In addition to the coarse lane it owns shared-runtime, Profile, macOS/Windows runtime, packaging, enterprise, release-verifier, app-smoke, and distribution dimensions. Workflow YAML must consume those outputs and must not duplicate path rules. Unknown paths or incomplete metadata fail closed to all affected platforms.
- Stage platform artifacts through a strict allowlist before upload. The macOS CI artifact contains only the DMG, blockmap, artifact receipt, and runtime-verification receipt; `.app`, temporary architecture trees, unpacked Python/native closures, `node_modules`, and other build directories make staging fail. Apply the corresponding minimal whitelist to Windows artifacts. Use `compression-level: 0` for already compressed installer payloads.
- Run each verification at the layer it owns exactly once. Source Profile checks run in the source job; packaged Profile/Loader checks run against final packaged bytes. Delete duplicate invocations instead of hiding them behind caches or higher timeouts.
- Minimize setup work: Enterprise uses a shallow sparse checkout without recursive submodules; dependency jobs fetch only their owned paths. Cache pnpm/Yarn stores, Electron binaries, electron-builder tools, NSIS/WinCodeSign/DMG tools, and Python wheels with keys bound to OS, architecture, Node/Electron/electron-builder versions, lockfiles, patches, installer inputs, and runtime manifests.
- Group changed native components by target so each target checks out, installs, and restores the Base SDK once. Split source preparation from source tests: source preparation emits the exact Base SDK, staged Profile, shared Desktop build, and receipts; source tests and affected platform jobs may then run in parallel, while admission waits for all required owners.
- Build platform-independent Desktop bytes once. Platform packagers consume a verified shared-build receipt bound to source commit, Base contract, input hash, and emitted file hashes. They must reject stale `lib` or mismatched Profile/Base bytes.
- Protected-main CI emits the unique release artifacts. Later Desktop/Profile/admission/publication stages download them by exact source SHA, run id, artifact id, byte count, and SHA-256; they verify, package where still required, sign, and publish without rebuilding accepted EXE/DMG/Base SDK/Profile/shared Desktop bytes. Optional performance diagnostics may consume the same candidate but never feed admission. A cache hit is never release evidence.
- Use Cache for reproducible dependencies and expensive intermediate carriers; use Actions Artifact for Base SDK, Profile components/generations, EXE/DMG, manifests, admissions, and receipts; use immutable object storage only for admitted production bytes. Every cache-restored carrier is rehashed and rebound to its receipt before use.
- A release coordinator may automate exact ID transfer and stage recovery from accepted CI through Profile, Desktop, admission, signing, and Cloudflare publication. Its only public inputs are source SHA, version, and release mode; it preserves environment approvals and emits an immutable `release-state.json` with no performance stage or performance receipt identity. Automation must not bypass approval, signing isolation, CAS activation, or make Feed/R2 writes from GitHub.
- Reuse a native carrier only when its fingerprint covers Electron, lockfiles, Yarn patches, app-builder patches, Python/Vision/native closures, builder configuration, installer scripts, and icons. An overlay may replace only admitted `app.asar`, Profile, or declared resources, then must rerun complete closure/hash verification and record both carrier and overlay provenance.
- Persistent or larger runners are an optimization after workflow waste is removed. A self-hosted macOS runner may execute only protected main/release code in a one-shot VM or restored snapshot; untrusted PR code never receives it, signing material, or production credentials.
- Do not optimize by raising timeouts, skipping installed-byte checks, rebuilding theoretically identical installers, treating cache as signed evidence, scattering path rules across YAML, using `continue-on-error`, rerunning unaffected platforms, or combining isolated signing/publication with build jobs. `desktop-publication.yml` keeps its fixed-SHA signer and exact three-file handoff.
- Apply pipeline work in this order unless measured evidence changes it: artifact whitelists; duplicate-check removal; sparse checkout/submodule reduction; Electron builder caches; PR distribution-build removal and target-grouped components; release consumption of exact CI artifacts; coordinator/stage recovery; only then larger or self-hosted runners.

## 2.0.11 failure ledger: permanent rules

- **Source tree is not the packaged product.** `registry.json`, dotfiles such as `.manifest.json`, nested `node_modules`, native prebuilds, architecture slices, and generated registries must be verified in the physical `afterPack` tree. `package:dir` and the formal carrier use the same runtime preparation path, and the Host/Profile/Client Loader plus required imports/helpers are smoked from those final bytes.
- **The CLI dependency tree is not the Desktop dependency tree.** A pnpm Harness patch does not prove Electron Builder's Yarn graph changed. Runtime behavior tests execute the final Desktop dependency bytes, and product Node/Python runtimes come only from the fixed Base; CI setup runtimes are build tools, never product authority.
- **One inventory and one visible owner.** The accepted component inventory drives composition, loading, packaging, publishing, and retirement. Each control, renderer, and state transition has one Slot/service/store owner. Native Agent messages stream outside the single collapsed running-process group; Think/Reasoning, Tool, Bash, and Context stay inside it; GenUI and native tool views remain delegated and compatible.
- **Session logs are a downstream compatibility boundary.** Every non-surface downstream event is written with explicit `ignorable: true`. Legacy recovery may recognize only an exact reviewed event allowlist; all other unknown events continue to fail closed. Acceptance includes write, exit, cold read, and an unknown-event negative test against the final Desktop graph; existing user logs are never rewritten in place.
- **Permissions are separate domains.** DSH sandbox, approval policy, plugin resource grants, OS TCC/helper identity, and credentials/Skill/MCP persistence neither imply nor overwrite one another. Computer Use acceptance requires the real packaged helper through authorize, restart/update, health, observe, and action; a UI label or process-alive check is insufficient.
- **External capability is end-to-end or unavailable.** A configured-looking button is not a working service. Sharing must prove create, restart/reload, public download, revoke, and 404/410; Skill Hub must prove publish, search, detail, install/enable, cross-session use, upload/delete, and permission boundaries. Unconfigured production services are shown as unavailable, not as successful local mocks.
- **Cross-Base selection happens before bootstrap validation.** Verify the signed public current release and target first, then select compatibility. Only an explicit `base-required` result permits a parentless complete bootstrap for the new Base; an already compatible current release rejects duplicate bootstrap.
- **Generated and cached state can be stale.** Cold CI must install every gate dependency explicitly. Generated bundles, profile projections, browser caches, Actions caches, and old website assets never override source and exact artifact provenance; verify the consumer-facing bytes after deployment.
- **Acceptance oracles do not own product defaults.** Executable smokes derive expected mode, graph, URL, version, and capability state from the same resolved owner contract as the product; they do not copy old literals. Every stateful smoke uses an isolated temporary `DSH_HOME`, is safe to run twice, and never reads or writes the operator's real sessions. When an owner default or composition changes, search its direct smokes and user-facing documentation for the retired value before freezing the candidate.
- **Performance claims need paired evidence.** TTFT and tok/s samples from one run are diagnostics, not parity proof. Compare the same model, prompt, network route, tools, warm/cold state, and production build against the accepted baseline before claiming no regression.
- **A release record names the exact truth stage.** Use only `source fixed`, `candidate built`, `installed accepted`, and `production released`. CI green, a signed plan, an uploaded subset, or a source screenshot must not be described as online. Missing platform evidence remains explicitly unverified.

## Definition of done

- `source fixed`: the root-cause regression and owning-component checks pass on the exact source SHA.
- `candidate built`: complete required artifacts/generations exist with exact run id, source SHA, byte count, manifest, and SHA-256 provenance; no production pointer changed.
- `installed accepted`: those exact immutable bytes pass the affected real installed user paths, permissions, restart, history cold-read, rendering, state, and rollback gates required by the lane. Performance results may accompany the record as diagnostics but are not required.
- `production released`: every immutable public object and stable pointer was read back and verified, the previous production install completed the natural-language update through its contracted platform path (atomic swap on macOS; standard assisted NSIS replacement on Windows), and the live download surface was checked when affected. Only this stage may be called "released" or "online".

## Work loop

1. Name the active slice in the development log.
2. Record newly verified facts before changing the implementation when they affect the architecture or release path.
3. Implement the smallest end-to-end path for the slice.
4. Run the narrowest test that proves the path, then its composition check.
5. Record commands, outcomes, remaining gaps, and the next slice.

The main agent owns acceptance. A child agent may repair one documented failure, but the main agent must rerun the failed scenario before closing it.
