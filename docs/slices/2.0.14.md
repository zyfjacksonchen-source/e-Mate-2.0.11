# e-Mate 2.0.14 single-hotfix contract

2.0.14 has exactly one product scope: restore four existing capability/Desktop contracts that can misroute ImageGen, fail the packaged connector launcher, lose the native Renderer environment, or prevent a published 2.0.12 macOS app from entering the current signed-update channel. No Goal, Canvas, Pet, icon, Better Sidebar, deliverable, audit-classification, schedule, model-policy, visual, or unrelated feature work may enter this release.

## Owner and invariants

1. `@e-mate/dsh-plugin-tool-search` keeps progressive discovery but must directly expose the existing first-party `imagegen` and `image_pack` Tools. The existing ImageGen leaf remains restricted by native `toolFilter`; it invokes `imagegen` directly and cannot use Skill discovery, CDP, browser Tools, or a second image dispatcher.
2. `@e-mate/dsh-plugin-find-skill` keeps the one approved connector installation path. When its fixed CLI command starts packaged pnpm, it must use the Desktop-provided Electron-as-Node executable, JavaScript entry and preloader directly on every platform; a generated `.cmd` or POSIX shell wrapper is not a raw-spawn executable.
3. `@e-mate/desktop` Main/Preload owns the immutable Renderer bootstrap for the main e-Mate window. Client code reads that bootstrap first; URL query remains a development/compatibility fallback and validated session storage remains only a legacy refresh fallback. External pages are still denied inside the e-Mate WebContents and never load the desktop client.
4. `@e-mate/desktop` selects an exact macOS update request envelope before protocol-specific validation. A fixed 2.0.12 predecessor may use only its exact 15-field request, old helper-ready/shutdown/health acknowledgement and rollback-safe swap; it never receives forged modern provenance or a pending-helper lease. The target version is the validated staged App version and must agree with request, running App and acknowledgement. The published 2.0.13 predecessor stays on the existing bound 24-field/pending/IPC path.
5. No prompt-body logging, provider credential, OAuth code, connector token, Tool arguments, user content, or private path is added to audit, receipts, or public diagnostics.
6. Existing Session, Agent, Tool, attachment, Job, Profile, update, credential and browser authorities remain unchanged. No capability lease framework, second router, second process runtime, second Renderer store or second updater is introduced.

## Required acceptance

- Image: initial tool surface includes `imagegen`/`image_pack`; one image leaf invokes `imagegen` without `tool_search`; multi-image leaves retain the same native allowlist; unrelated deferred Tools stay hidden; edit/fusion/source attachment and failure receipts keep existing semantics.
- Connector launcher: generated component test proves packaged pnpm becomes direct Electron-as-Node argv with the isolated environment; non-pnpm commands retain the native subprocess path; Desktop tests prove publication and disposal of the exact immutable launch inputs on POSIX and Windows.
- Renderer: Main-created BrowserWindow carries one validated main-window bootstrap; Preload exposes it through context isolation; client prefers it over malformed/missing query state; query-only development and session-storage legacy fallback remain tested; external navigation/window creation stays denied.
- macOS update: the exact published 2.0.12 App must create its old request and update through the candidate Helper to 2.0.14; failed candidate health must restore 2.0.12. The exact published 2.0.13 App must update to the same 2.0.14 bytes through the unchanged bound protocol. Both retain Profile, sessions and user data.
- Release: the repository classifier selects the actual affected lane. Only checks and package/install/update/rollback scenarios covering these owners run. Production may use only protected-main attempt-1 exact bytes and the exact external publication owner pinned above. After immutable/public readback and signed-pointer CAS, `desktop/latest.json` may advance exactly once from the frozen 2.0.13 identity to those same 2.0.14 manifest bytes, then becomes the new frozen bridge pointer. Release notes describe only reliability fixes and expose no internal plugin names.
