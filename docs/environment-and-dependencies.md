# Environment and dependencies

## User environment

Users install and run e-Mate with Node.js and npm only. Supported Node versions are `^22.19.0` and `>=24`; Node 24 LTS is the release build baseline. The CLI rejects unsupported platforms and incomplete resource closures before `setup` changes the profile or user data.

The finished release must not require pnpm, Python, Xcode, MSVC, Rust, Electron, signing tools, or a separately downloaded browser. Microsoft Office is optional for opening a downloaded document. Office authoring support is supplied as Skills and is not considered ready until its host toolchain passes the relevant platform acceptance.

## Development environment

- Node: `24.x` from `.nvmrc`.
- Package manager: Corepack and exact `pnpm@11.7.0` from the root `packageManager` field.
- TypeScript/JavaScript dependency lock: committed `pnpm-lock.yaml`.
- Main source: TypeScript/TSX; Node ESM and browser JavaScript are generated by the exact target `tsdown@0.22.2` installation.
- Harness: exact source commit `zyfjacksonchen-source/deepseek-harness@df78045a127e32cb5b942defba52c539590d1596`, based on upstream `99f6f02fecdb7dff40c3fbc9470f5907c29f74ca`; its declared version remains `0.1.0-rc.7`.
- Browser client bundles: built with the pinned Harness `clientBundle` tsdown preset so module IDs, external identities, CSS ownership, source maps, and Cordis loading semantics remain compatible.
- Shell visual source: exact e-Mate 2.0.5 submodule commit `564a6b6c1d43fb6831dd4a5cd8026e472f063311`.

## Release package topology

The public release closure is one npm package:

| Package | Contents | Current status |
| --- | --- | --- |
| `@e-mate/dsh@2.0.7` | TypeScript CLI, pinned Harness closure, browser overlay, profile, and embedded bundle registry | Commit `f9c50fe` single-tarball candidate passed CI pack/evidence and clean npm install on darwin-arm64, darwin-x64 and win32-x64; registry/R2 publication and real Windows/macOS-x64 Computer Use remain open |

There are no `@e-mate/dsh-runtime-*` or `@e-mate/dsh-browser-*` packages and no platform `optionalDependencies`. The deleted Python/Office/OCR Worker, RapidOCR models, Playwright Chromium payload, and their postinstall/build scripts are not part of 2.0.7. Setup validates the main package, Harness receipt, embedded bundle manifests, profile composition and platform capability state; it never restores the deleted closure or downloads a browser.

The main tarball embeds the generated files declared by ten profile bundles: `office-skills`, `search-mcp`, `browser`, `browser-panel`, `vision-toolkit`, `memory-evolve`, native-subagent receipt, `genui`, `better-sidebar`, and the fail-closed `dsh-im` adapter receipt. Setup copies only their allowlisted package files into the managed profile and uses the target Loader/bundle patches. A bundle manifest, version, main entry or registry mismatch stops setup. The `dsh-im` receipt has no runtime dependency; its audited upstream runtime stays outside the install closure until every licensed channel dependency and the pinned rc.5/project binding contract pass.

Browser control uses the same bundled `dsh-browser` MV3 extension on macOS Chrome and Windows Chrome/Edge. The extension has no side-panel chat, model, settings, Session gateway or approval UI; it connects to a loopback token-authenticated Tool carrier and executes only target-authorized calls bound to the real Session ID. It uses the installed browser and contains no Chromium/Playwright/Ego runtime. macOS or Windows remains `setup-required` until the corresponding real extension, session isolation, interaction, download, teardown and Browser Panel acceptance closes; package presence alone is not readiness.

The required Harness rc.5 package family is not available as that version on npm. `scripts/build-harness-runtime.mjs` therefore uses the target repository's own `pnpm deploy` and `release:pack` paths, materializes the complete DSH/vendor peer set, runs the target's reviewed subprocess postinstall, removes package-manager links, and writes a source/lock receipt. The resulting `runtime/harness` tree is included in the main tarball; changing to a registry rc.6 is forbidden.

The assembler requires exact `pnpm@11.7.0`, rejects a Harness commit/version mismatch, builds beside the destination, runs the packaged `dsh --version` before activation, and only then atomically replaces the previous generated closure. Generated runtime bytes are release artifacts and remain ignored by Git; the source, lock, assembler and receipt contract are reviewed instead.

## Release evidence and publication carrier

`.github/workflows/ci.yml` validates the source on Node 24. The release workflow follows the pinned Harness CI-first contract: every pull request performs a credential-free build and pack, installs the resulting single tarball into a clean consumer outside the checkout, and preserves that exact candidate. Supported-platform lanes run their own setup and capability probes against the same bytes; they do not build separate native npm packages. A protected manual publish consumes the accepted candidate without rebuilding.

Release evidence covers the one package identity/version/target pin, embedded bundle registry, `SHA256SUMS`, `release-manifest.json`, SPDX 2.3 SBOM, aggregated third-party licenses and evidence checksum. Publication requires the accepted S12 commit SHA to equal the workflow commit. The already-published registry `@e-mate/dsh@2.0.7` is never overwritten or reused as a fallback; the accepted replacement tarball and evidence are admitted only under the new commit-scoped `npm/candidates/v2.0.7/<source-commit>/` Cloudflare R2 prefix. `EMATE_R2_PUBLIC_ORIGIN` is pinned to `https://pub-ada3f610c0234a76838f4e19fe2bb25e.r2.dev`; authenticated metadata and public range reads must match local size and SHA-256 before admission. The workflow does not activate the download, management or audit URLs; that remains a separate production action after real Computer Use and the R2 receipt.

## Pinned Harness capability boundary

A source audit at the pinned Harness commit establishes the dependency boundary for S01 and S10:

| Capability | Reuse from Harness | e-Mate-owned gap |
| --- | --- | --- |
| Web search | Reuse Harness Web/Tool contracts through `search-mcp` | No duplicate browser transport or legacy search Tool |
| HTTP fetch | Reuse the native `@deepseek-ai/dsh-web-fetch-http` provider only after the e-Mate profile explicitly enables it and its security limits are accepted | No legacy fetch duplicate; it is not Computer Use and does not read PDF/binary bodies |
| Browser Computer Use | `dsh-browser` MV3 carrier; Harness Tools, approvals, Session ID and events remain authoritative | Existing macOS Chrome or Windows Chrome/Edge; each platform remains setup-required until real acceptance |
| OCR/Vision | Reuse target Tool/model-policy composition through `vision-toolkit` | `blocked`: rc.5 lacks the required enterprise model-policy seam; no local Worker/model fallback |
| Office/PDF | Register the four clean-room `office-skills` through the target Skill registry | `blocked`: no legally distributable packaged execution layer; no host-toolchain probing or fake artifact fallback |
| Memory | Use `memory-evolve` with WorkspaceRegistry/session binding | No standalone dream/learning store or global scope |
| Subagents | Reuse rc.5 native Subagent services | Receipt only; no copied AGPL implementation |
| Generated UI/sidebar | Use `genui` and `better-sidebar` target slots | No second router, Store or client transport |

Harness's Playwright dependency belongs to its Web UI test setup; it is not product Computer Use. The selected Windows adapter therefore has its own exact MCP version and must pass the target permission/workspace and Edge acceptance gates without downloading a browser. This is a deletion rule as well as an installation rule: missing capabilities stay blocked rather than reviving the removed Runtime/Browser family.

## Data and profile directories

Resolution order is explicit configuration, `DSH_HOME`, then `~/.dsh`. Mutable data never lives in the global npm installation:

```text
$DSH_HOME/
├── profiles/
│   └── e-mate/
│       ├── package.json
│       ├── cordis.patch.yml
│       └── node_modules/       # managed profile-local plugin overrides
└── e-mate/
    ├── sessions.sqlite3
    ├── state.sqlite3
    ├── attachments/
    ├── memory/
    ├── cache/
    ├── migrations/
    ├── run/
    └── logs/
```

Harness maintains an installation fallback at `$DSH_HOME/profiles/node_modules`. e-Mate-owned UI/plugin replacements live in the nearer profile-local `profiles/e-mate/node_modules`, using the target Loader's normal Node resolution rather than a custom loader.

Profile bundles use the exact target registries and services instead of bundling a second Tool, Skill, Job, Storage, Router or Connection implementation. `setup` installs only bundle files declared by the generated registry and verifies their package name, version and entry point. A missing, moved or changed target module fails plugin setup; there is no copied registry or compatibility fallback.

`memory-evolve` opens its storage through the target Storage Domain and binds each project record to the stable Harness workspace ID plus canonical-path SHA-256. The current session must be a member of that binding; a general conversation receives a session-only scope. It does not create SQLite, a second event log, model client, Job registry, dream store, learning store or profile-local database.

The four Office identities are disabled Skills, not a bundled document runtime. They report `EMATE_OFFICE_EXECUTION_LAYER_UNAVAILABLE`, are neither model- nor user-invocable, register no execution Tool, and never probe an accidental host Office/Python/LibreOffice installation. They may become active only when a separately licensed macOS/Windows plugin supplies the complete prebuilt execution layer through target Tool/Job/filesystem seams and passes real DOCX/PDF/XLSX/PPTX create/read/edit/export/reopen acceptance.

Browser state, page results and downloads may be exposed only through the `dsh-browser` carrier's real target Session/Tool/attachment path. Until each supported platform passes acceptance, setup keeps that platform and Browser Panel at `setup-required`; no unverified session isolation or download behavior is claimed.

Image generation has no local provider runtime or packaged model Key. It calls the existing fixed HTTPS e-Mate Model Gateway `/v1` root through `emateIdentity`; generation uses `/v1/images/generations`, editing uses `/v1/images/edits`, and both are fixed to `gpt-image-2-pro`. Results and references use the target attachment store. If that root is absent or malformed, the profile remains loadable but does not register `imagegen`. This is a required failure, not a fallback to production material, a browser credential, system environment, legacy Python image Skill, the older incompatible Image Job JWT, or a guessed download-domain path.

The browser and local runtime always use the HTTPS Model Gateway. A production route may use an operator-approved HTTP provider only by setting the server-only literal `allowInsecureHttpUpstream: true` beside that route's credential-free `upstreamBaseUrl`; omission stays HTTPS-only, keys remain external secret files, redirects are rejected, and neither the URL nor the opt-in is returned by `/v1/models`. This explicit exception does not encrypt the Gateway-to-provider hop, so it is limited to the network path the operator has separately accepted.

## Credentials and external tools

macOS credentials use Keychain and Windows credentials use DPAPI. Files contain only non-secret credential references. The enterprise model policy and model credentials are never bundled into npm or browser state.

External MCP/CLI processes may launch only through target subprocess and permission contracts, with explicit argv, cwd/workspace scope and environment allowlists. Install and setup cannot run `pip install`, download a browser, install Chromium, or compile native code on the user machine. Browser Computer Use uses only the packaged `dsh-browser` MV3 extension and the user's existing supported browser.

## Upgrade invariants

Setup validates the new main tarball, fixed Harness receipt and complete embedded bundle registry before snapshot or migration. Same-version setup repairs managed profile files and the shortcut idempotently. A new version refuses active runs, snapshots mutable data, applies idempotent migrations, writes a receipt, health-checks the new version, and only then activates it. Failure restores the snapshot and leaves the new version inactive; downgrade is opt-in and snapshot-bound.

Manual and Agent-requested updates share this one transaction. The Agent calls the typed `e-mate update` command through Harness's existing Bash/PowerShell Tool; it does not synthesize npm, migration or restart commands. A detached helper is required because the running Host cannot replace its own files safely, especially on Windows. The helper uses the npm executable paired with the active Node installation, never a browser API or system package manager, and writes redacted receipts below `$DSH_HOME/e-mate/migrations/`.

Activation and rollback derive the current global npm prefix from the managed package path and explicitly reuse it; an unrecognized local or non-global layout fails before mutation. The detached Helper revalidates the persisted request ID, target and current SemVer before they can reach npm. The single tarball is installed without running a browser/Python bootstrap because none exists in the release closure. npm's exact `dist.integrity` must be a SHA-512 SRI value for both staged and previous versions; the private terminal receipt records both values while the public status projection omits them. Rollback is armed before npm starts replacing the global package so a partial npm failure cannot be misclassified as a pre-change failure. The newly installed CLI version must equal the staged version before setup, and a failed update restarts the previous instance on its original managed port.

`e-mate status` projects the latest validated `online-update-*.json` receipt as `latest_update`. The projection contains only request ID, terminal status, requested/previous/installed versions and completion time; npm error output, paths and environment values remain in the local mode-0600 receipt/log. An Agent must match this request ID to the one returned by `e-mate update --json` before reporting completion.

Only one detached update helper may own `$DSH_HOME/e-mate/run/update.lock`. A second request fails while the recorded PID is alive; a lock whose owner process no longer exists may be reclaimed. Lock handoff is request-ID- and PID-bound, and the helper removes only its own lock after writing the terminal receipt, preventing concurrent npm replacement and overlapping data snapshots.
