# Environment and dependencies

## User environment

Users install and run e-Mate with Node.js and npm only. Supported Node versions are `^22.19.0` and `>=24`; Node 24 LTS is the release build baseline. The CLI rejects unsupported platforms and incomplete resource closures before `setup` changes the profile or user data.

The finished release must not require pnpm, a system Python, a system Chrome, Xcode, MSVC, Rust, Electron, or signing tools. Microsoft Office is optional for opening a downloaded document, not for creating, reading, editing, or exporting one.

## Development environment

- Node: `24.x` from `.nvmrc`.
- Package manager: Corepack and exact `pnpm@11.7.0` from the root `packageManager` field.
- TypeScript/JavaScript dependency lock: committed `pnpm-lock.yaml`.
- Main source: TypeScript/TSX; Node ESM and browser JavaScript are generated by the exact target `tsdown@0.22.2` installation.
- Harness: exact source commit `47f943859bef60e4160492346772ded9b24f765a`; its declared version is `0.1.0-rc.5`.
- Browser client bundles: built with the pinned Harness `clientBundle` tsdown preset so module IDs, external identities, CSS ownership, source maps, and Cordis loading semantics remain compatible.
- Shell visual source: exact e-Mate 2.0.5 submodule commit `564a6b6c1d43fb6831dd4a5cd8026e472f063311`.

This does not substitute for darwin-x64 or win32-x64 runner evidence.

Browser packages are generated from the exact Playwright installation already locked by the Harness Web application (`playwright@1.61.1`, Chromium revision `1228`, browser `149.0.7827.55`). They carry the revision's headless shell and notices, not a system Chrome. The reviewed package postinstall only restores executable bits stripped by npm tar normalization; it does not download, compile or modify user data. `setup --check` launches the packaged browser with an ephemeral profile and requires the real DevTools-ready signal before reporting success.

The main package depends on exact `playwright-core@1.61.1`, the protocol library selected by that same Harness lock. `playwright-core` has no browser-download postinstall. Setup records and hashes its resolved entry point in the managed profile binding. The Computer Use plugin launches only the platform package's manifest-verified Chromium through `ctx.subprocess`, then uses that exact library solely to connect over the loopback DevTools endpoint. Playwright never selects a system browser, downloads an engine or owns an untracked process tree.

Runtime packages are generated from the final e-Mate 2.0.5 Office/OCR Worker at commit `564a6b6c1d43fb6831dd4a5cd8026e472f063311`. A `uv@0.11.7` universal hash lock constrains the eight required roots to the exact 2.0.5 platform-stage lock and produces a 29-package cross-platform closure (27 distributions on macOS; two entries are Windows-only). Build hosts install that lock into a pinned relocatable CPython 3.11.15 from python-build-standalone release `20260602`; user installation runs no Python installer. The package manifest records the complete payload tree digest, the six packaged ONNX models, distribution inventory, interpreter, Worker, source/lock identities, and executable list.

npm tar omits symbolic links. The Runtime build therefore removes the standalone archive's convenience links before calculating its payload identity and points the public manifest at the real interpreter file. Postinstall restores only the manifest-listed executable modes. `setup --check` then recalculates the entire Runtime tree, validates every OCR model hash, and executes isolated Office and OCR Worker probes with an environment allowlist; Boolean manifest declarations cannot satisfy those checks.

The Runtime build also removes pip-generated console entry scripts and their `RECORD` rows because those scripts embed the random staging path in their shebang. Every build-time Python invocation uses `-B` and `PYTHONDONTWRITEBYTECODE=1`, so relocatable stdlib bytecode cannot capture the staging directory. Two consecutive darwin-arm64 builds then produced the same 6,803-file payload SHA-256, `8ed54dadde01aac9d57ec15af6816efb812b0b44ab481835d027ba121d597a28`. The manifest separately pins Python SHA-256 `e3938f2a272dafdc33f3dd12b093dfc85354629476cb97a7d7d4a7201b8482dd` and Worker SHA-256 `257f21d5bb8ef16151027e006a3c38aaa15bf9f2e2a4fc541c7946ddf339d891`. The current darwin-arm64 npm tarball is 135 MiB with SHA-256 `9eff1a480b560c16f2c5cf45fb6b2b53959bef730fe54fca6bba28fb32a7e856`.

The required Harness rc.5 package family is not available as that version on npm. `scripts/build-harness-runtime.mjs` therefore uses the target repository's own `pnpm deploy` and `release:pack` paths, materializes the complete DSH/vendor peer set, runs the target's reviewed subprocess postinstall, removes package-manager links, and writes a source/lock receipt. The resulting `runtime/harness` tree is included in the main tarball; changing to a registry rc.6 is forbidden.

The assembler requires exact `pnpm@11.7.0`, rejects a Harness commit/version mismatch, builds beside the destination, runs the packaged `dsh --version` before activation, and only then atomically replaces the previous generated closure. Generated runtime bytes are release artifacts and remain ignored by Git; the source, lock, assembler and receipt contract are reviewed instead.

## Release evidence and publication carrier

`.github/workflows/ci.yml` validates the source on Node 24. `.github/workflows/release.yml` builds the two matching platform packages on each of `macos-15` (arm64), `macos-15-intel` (x64), and `windows-2025` (x64), packs the main package once, and clean-installs the main plus the matching platform pair before evidence assembly. It never attempts to emulate a foreign platform package on the wrong host.

`scripts/release.mjs` accepts exactly the six platform tarballs and the main tarball. It rejects a package identity, version, OS/CPU, target-pin or exact-optional-dependency mismatch, then produces `SHA256SUMS`, `release-manifest.json`, SPDX 2.3 SBOM, aggregated third-party license evidence and an evidence checksum. Runtime distribution records retain their package name, version, license and source metadata so Python contents are not reduced to an opaque binary payload.

Publication is GitHub-Actions-only, requires the accepted S12 commit SHA to equal the workflow commit, and publishes the six platform packages before the main package. Registry readback is fail-closed: identical existing bytes are idempotent, different bytes at the same name/version stop the release, and the public package is clean-installed again after publication. The exact seven tarballs and five release-evidence files are then admitted as immutable objects under `npm/v2.0.7/` in the existing Cloudflare R2 bucket. `EMATE_R2_PUBLIC_ORIGIN` is a release-environment value and must be a credential-free HTTPS custom domain already bound to that bucket; production rejects `*.r2.dev` and `*.r2.cloudflarestorage.com`, and never infers the origin from the application server. Authenticated R2 metadata and public first/last-byte ranges must match the local size and SHA-256 before the deterministic admission receipt is written. An existing object with different size or digest is a collision and stops publication. The stable download URL is only an entry/integrity page; final package bytes come from the admitted R2 object URLs. The workflow intentionally does not activate the download, management or audit URLs; that remains a separate production action after real Computer Use and the R2 receipt.

## Pinned Harness capability boundary

A source audit at the pinned Harness commit establishes the dependency boundary for S01 and S10:

| Capability | Reuse from Harness | e-Mate-owned gap |
| --- | --- | --- |
| Web search | Reuse `ctx.web`, `@deepseek-ai/dsh-web-search-deepseek`, and the model-facing `web_search` Tool | No duplicate search service or legacy search Tool |
| HTTP fetch | Reuse the native `@deepseek-ai/dsh-web-fetch-http` provider only after the e-Mate profile explicitly enables it and its security limits are accepted | No legacy fetch duplicate; it is not Computer Use and does not read PDF/binary bodies |
| Browser Computer Use | Reuse Harness Tools, Jobs, attachments, events, and Cordis registration | Provide only the missing browser-control adapter and the packaged pinned Chromium runtime |
| OCR | None exists in Harness | Provide the Cordis adapter, portable Python Worker, RapidOCR/ONNX dependencies, and model resources |
| Office/PDF | None exists in Harness | Provide the Cordis adapter, portable Python Worker, and locked DOCX/XLSX/PPTX/PDF libraries |

Harness's Playwright dependency belongs to its Web UI test setup; it does not ship an Agent browser-control Tool. The Python SDK runtime packages similarly serve the optional Harness Python SDK subprocess and are not required by e-Mate's Node CLI closure. They must not be added merely because e-Mate retains an internal Python Worker for Office/OCR.

This is a deletion rule as well as an installation rule: target-native search/fetch remains target-owned, while only capability gaps receive e-Mate adapters. Runtime/Browser packages cannot be removed until equivalent target functionality exists and passes the same acceptance suite.

## Data and profile directories

Resolution order is explicit configuration, `DSH_HOME`, then `~/.dsh`. Mutable data never lives in the global npm installation:

```text
$DSH_HOME/
├── profiles/
│   └── e-mate/
│       ├── package.json
│       ├── cordis.patch.yml
│       └── node_modules/       # managed profile-local plugin overrides
└── e-mate/
    ├── sessions.sqlite3
    ├── state.sqlite3
    ├── attachments/
    ├── memory/
    ├── cache/
    ├── migrations/
    ├── run/
    └── logs/
```

Harness maintains an installation fallback at `$DSH_HOME/profiles/node_modules`. e-Mate-owned UI/plugin replacements live in the nearer profile-local `profiles/e-mate/node_modules`, using the target Loader's normal Node resolution rather than a custom loader.

Profile plugins must also use the exact target Tool constructor instead of bundling or resolving a second copy of `@deepseek-ai/dsh-tools` from the mutable profile directory. `setup` resolves that module from the verified packaged Harness CLI, records its absolute path, SHA-256 and pinned Harness commit in the mode-0600 managed Runtime binding, and the Office/OCR and Skill Hub plugins validate that binding before dynamic import. A missing, moved or changed target module fails plugin setup; there is no copied Tool registry or compatibility fallback.

Project memory uses the same managed binding for the pinned Harness `@deepseek-ai/dsh-storage-domain` entry and its exact `zod@4.4.3` schema runtime. Dream distillation and autonomous learning additionally bind the pinned `@deepseek-ai/dsh-llm` entry by absolute path and SHA-256, then call the already-composed `ctx.llm` and `ctx.jobs` services. The plugins open one `emate_memory` domain through the target JSON backend; they do not create SQLite, a second event log, model client, Job registry, or profile-local database. Records store a stable Harness workspace ID plus the SHA-256 of its canonical path, never the path itself. An unregistered session receives only a session-ID-derived scope.

Office output is immutable product data under `$DSH_HOME/e-mate/attachments/office`: the Worker first validates the generated document, then e-Mate writes a content-addressed artifact plus a receipt containing name, MIME type, size and SHA-256. Read and edit reopen the artifact by ID; edit always produces a new artifact and never overwrites its source. Harness rc.5 attachments currently represent images only, so verified Office bytes use a loopback-only `GET/HEAD /api/e-mate/office.download` route following the target Session Export pattern. The route rechecks size and SHA-256 and returns `no-store`, `nosniff` and a safe attachment name.

Browser state is keyed by the hash of the authoritative Harness session ID and stored under `$DSH_HOME/e-mate/browser/sessions/`; a Tool call without a live session fails instead of falling back to a global profile. Continuing that session reuses its cookies/local state, while a different session cannot read the profile through the Tool contract. Screenshots are committed through `ctx.attachments`. Downloads are capped at 100 MiB and committed to an immutable SHA-256 store under `$DSH_HOME/e-mate/attachments/browser`; their loopback download receipt is revalidated before each `GET/HEAD` response.

Image generation has no local provider runtime or packaged model Key. It calls the existing fixed HTTPS e-Mate Model Gateway `/v1` root through `emateIdentity`; generation uses `/v1/images/generations`, editing uses `/v1/images/edits`, and both are fixed to `gpt-image-2-pro`. Results and references use the target attachment store. If that root is absent or malformed, the profile remains loadable but does not register `imagegen`. This is a required failure, not a fallback to production material, a browser credential, system environment, legacy Python image Skill, the older incompatible Image Job JWT, or a guessed download-domain path.

## Credentials and subprocesses

macOS credentials use Keychain and Windows credentials use DPAPI. Files contain only non-secret credential references. The enterprise model policy and model credentials are never bundled into npm or browser state.

Platform Workers launch from manifest-verified absolute paths. They receive an explicit environment allowlist and do not inherit unrelated provider or enterprise credentials. Install and setup cannot run `pip install`, download a browser a second time, or compile native code on the user machine.

On Windows, Worker process memory containment remains a release blocker. The legacy Worker assumes its parent applies a Windows Job Object limit, while the pinned Harness local subprocess runtime currently proves process-tree termination but not an equivalent memory cap. The win32 Runtime package and Windows Office acceptance cannot be marked complete until that boundary is adapted through the target subprocess path and exercised on Windows; e-Mate must continue to fail closed meanwhile.

## Upgrade invariants

Main, Runtime, and Browser package versions must match exactly. Setup validates the full new closure before snapshot or migration. Same-version setup repairs managed profile files and the shortcut idempotently. A new version refuses active runs, snapshots mutable data, applies idempotent migrations, writes a receipt, health-checks the new version, and only then activates it. Failure restores the snapshot and leaves the new version inactive; downgrade is opt-in and snapshot-bound.

Manual and Agent-requested updates share this one transaction. The Agent calls the typed `e-mate update` command through Harness's existing Bash/PowerShell Tool; it does not synthesize npm, migration or restart commands. A detached helper is required because the running Host cannot replace its own files safely, especially on Windows. The helper uses the npm executable paired with the active Node installation, never a browser API or system package manager, and writes redacted receipts below `$DSH_HOME/e-mate/migrations/`.

The updater must allow the packaged Runtime and Browser `postinstall` scripts in staging, activation and rollback. Those reviewed scripts perform only manifest-bounded executable-bit restoration and make no network request, download or build; using npm `--ignore-scripts` would leave the packaged Python or Chromium non-executable on macOS. Activation and rollback derive the current global npm prefix from the managed package path and explicitly reuse it; an unrecognized local or non-global layout fails before mutation. Rollback is armed before npm starts replacing the global package so a partial npm failure cannot be misclassified as a pre-change failure. The newly installed CLI version must equal the staged version before setup, and a failed update restarts the previous instance on its original managed port.

`e-mate status` projects the latest validated `online-update-*.json` receipt as `latest_update`. The projection contains only request ID, terminal status, requested/previous/installed versions and completion time; npm error output, paths and environment values remain in the local mode-0600 receipt/log. An Agent must match this request ID to the one returned by `e-mate update --json` before reporting completion.

Only one detached update helper may own `$DSH_HOME/e-mate/run/update.lock`. A second request fails while the recorded PID is alive; a lock whose owner process no longer exists may be reclaimed. Lock handoff is request-ID- and PID-bound, and the helper removes only its own lock after writing the terminal receipt, preventing concurrent npm replacement and overlapping data snapshots.
