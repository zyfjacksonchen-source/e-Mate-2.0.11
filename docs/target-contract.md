## First development principle: native Creation Mode before permanent plugins

- “对照 DSH 原生” always means the Harness and Desktop-reference pins declared by the current checked-in `desktop/e-mate-desktop/base-contract.json`, never a floating upstream branch, latest package, another RC, or an unrelated Desktop release. Before implementation, the development record names the exact e-Mate Base id, Harness version/commit, and Desktop-reference commit used as evidence; component locks, runtime imports and composition tests must resolve to those same pins or fail closed.
- The pinned rc.7 `cordis` preset (“创造模式”) is the first development path for every feature that can be expressed as a DSH Host or Client plugin. Development starts by loading the shipped plugin/composition authoring skill, querying the live runtime with the native `cordis_inspect_*` providers, and exercising the smallest reversible dynamic package through the native define/run/stop/undefine lifecycle. Runtime Services, Events, Tools, Slots, themes, and lifecycle reports are authoritative; screenshots and guessed interfaces are not.
- A dynamic Cordis package is only a process-local prototype. It is not a Profile component, does not survive restart, cannot be promoted by copying memory state, and cannot bypass repository admission. The accepted result must be reimplemented as an ordinary immutable Profile plugin and pass exact Base/Harness compatibility, component and composition tests, signature and provenance validation, atomic generation activation, renderer-health commit, and rollback.
- Desktop preserves the complete shipped system-preset root from the pinned DSH package, including `standard`, `code`, `minimal`, and `cordis`, as the reference Desktop does. e-Mate may shadow only `standard` from a separate managed system root to supply the product persona. The ordinary product UI hides preset selectors and the preset-management page, but it must not edit, remove, or disable the shipped preset tree or make Creation Mode the default; `cordis` remains available to the native Agent/development path required by this contract.
- Creation Mode has shell-equivalent trust and is explicit opt-in. Dynamic code receives no signing secret, component publication credential, desired-state activation authority, or automatic production deployment path. Electron lifecycle, native helpers, platform packaging/signing, updater trust, and any other Base-only behavior remain on the pinned `deepseek-harness-desktop` path; inability to model them dynamically is recorded rather than concealed behind a fake plugin.
- Repository gates must fail if the shipped `cordis` preset and its two authoring skills are absent from the packaged runtime, if Desktop composition replaces the shipped preset root with a single custom preset, or if a dynamic-package directory/source becomes a release payload. The development log records the inspected seam, experiment outcome, permanent component mapping, and narrow acceptance command for each applicable slice.

An incompatible release checks the existing Base lane and otherwise returns `base-required`; it never attempts a speculative plugin install.
- Project memory is scoped by the pinned Harness `WorkspaceRegistry` identity and its canonical workspace path. Memory, dream distillation, learning output, and imported CowAgent material for workspace A must never be read from or written to workspace B; an ungrouped session receives session-local scope rather than a shared fallback. A missing, moved, or mismatched workspace binding fails closed.
- Every visible interactive UI element must complete a real Harness or enterprise-boundary action and expose its pending, success, failure, cancellation, and reloaded state. Empty handlers, placeholder links, fake success, permanently inert buttons, and visual controls with no reachable terminal result are release blockers.
- Permission domains remain separate. A DSH sandbox preset controls only the effects defined by the pinned sandbox policy; `danger-full-access` does not grant macOS TCC, Computer Use application leases, the CDP plugin's independent browser-control setting, credentials, network accounts, Skill installation, MCP process persistence, or another plugin-owned capability. The product baseline enables the endpoint-bound CDP setting and lets the user revoke it; this default remains independent of Full Access and never bypasses Chrome's own remote-debugging switch. The approval policy is a second independent domain: `approval/policy: never` rejects operations that require `ctx.approval` and must never be interpreted as automatic consent. Each plugin must use the pinned native authorization seam for its own resource and fail closed when that authorization is absent.
- Each Profile component declares one closed-vocabulary `authority_contract` (`effects` plus `guards`) in its package metadata; the deterministic emitter binds the exact same object into the signed component manifest and the Desktop parser rejects schema or vocabulary drift. The contract records and discloses authority but grants none: Cordis Host JavaScript is trusted in-process code, and sandbox, approval, plugin settings receipts, credentials, OS privacy grants, and authenticated remote accounts remain the only runtime authorities.
- Identity begins with self-registration, not administrator-created credentials. Registration requires a unique account, mandatory real name, a 10–256 character password, and a one-time expiring enterprise image-verification challenge. The enterprise server rate-limits challenge issuance and submission; successful submission creates only a `pending_approval` record and never a login lease.
- An administrator may list, inspect, approve, edit, disable, and soft-delete identity records through the existing management workspace. Approval is invalid until a positive per-user weekly Token limit and a valid model policy are configured. Disabled/deleted users and users without that allowance cannot log in; changing status, allowance, password, or deletion state increments the auth revision and revokes active leases. These operations remain inside `emate.identity`/`emate.modelPolicy` and grant no local-runtime control.
- Login carries an explicit `remember_login` boolean. It changes only the server-issued lease lifetime; the browser never persists a password, bearer, refresh token, or model credential. With it disabled, closing the authenticated browser context or ordinary lease expiry requires login again; with it enabled, the Host may restore an unexpired OS-keystore-backed lease after browser restart.
- Password login, logout, and password change retain the existing e-Mate request/receipt contracts. A successful change revokes prior account leases, returns `reauthentication_required`, rejects the former password, and permits a new login only with the new password; plaintext passwords never enter browser persistence, logs, audit, or receipts.
- Usage acceptance reconciles provider-reported immutable usage facts, the local durable audit outbox, the enterprise receipt, account counters, and the existing usage panel. Duplicate delivery is an idempotent no-op; a missing or conflicting fact is surfaced as a data-quality failure and cannot be hidden by an aggregate total.

## Compatibility and delivery

### Base and Profile component boundary

- “Everything is a plugin” means product behavior is delivered through ordinary DSH Profile bundles, client slots, and generated assets. It does not authorize changes to the pinned Harness source, a second plugin loader, a second update service, or Desktop-owned platform lifecycle code inside a product plugin.
- The Desktop base is the immutable native carrier: Electron, the pinned Harness/runtime closure, the existing Desktop startup and shutdown lifecycle, updater trust root, native helpers, and platform packaging/signing inputs. Browser behavior belongs to the CDP Profile component, not the Base. A Base release retains the 2.0.10 macOS arm64 interactive-shell, x86_64/Rosetta native-readiness, Windows renderer-health, closure, signature, clean-start, and warm-start gates.
- Base v7, its SDK receipt, every compatible Profile component and the public Desktop release manifest bind `schedule_protocol_floor: 1`. The updater rejects a missing, invalid or lower floor before requesting or staging payload bytes, accepts a higher positive floor only through a newer signed Base, and rechecks the exact floor and Base identity after user confirmation.
- Installed-app startup is gated against the accepted 2.0.11 installed artifact, not an absolute ceiling. On the same machine and architecture, use the same install/copy state, authentication/Profile state, launch command and probe boundary for one clean launch and three warm launches of both artifacts; for the clean sample, warm p75 and warm maximum, `candidate - paired 2.0.11 baseline` must be at most `10,000 ms`. An unauthenticated launch reaches the real visible, AX-readable, clickable login form at the paired probe boundary; its AURA renderer is statically bundled and eagerly mounted with the login route, never fetched or dynamically imported at login time, and failure or delay of WebGL cannot block identity input.
- An official Profile component is one immutable package or product Profile layer with its own id, version, byte count, SHA-256, provenance, and exact compatibility declaration. Third-party Profile dependencies and bundles remain a separate user-owned overlay; an official update must not install, remove, enable, disable, reorder, or upgrade them.
- A portable Profile component has `target: null`. A platform Profile component is independently releasable only when the inventory, component manifest and signed desired state bind the same exact tuple: `platform`, `arch`, native `runtime_abi`, `minimum_os`, signing scheme/identity and sorted native closure. The authoritative matrix is `darwin-arm64`, `darwin-x64` and `win32-x64`; each target builds and tests on its matching runner and emits only that target's native bytes. The client selects a platform/architecture desired state before download and rejects a mismatched tuple, native closure, binary format or signing declaration. `minimum_os` records the native capability floor; a capability below that floor stays unavailable without blocking unrelated portable components in the same generation.
- Compatibility is an explicit tested contract id, never an inferred SemVer range. A component manifest lists the exact accepted Desktop base contract ids and Harness contract id. For example, a component tested only with an rc.7 base is not offered to an rc.6 base. If the installed base is not explicitly listed, update selection must choose a compatible Base release; if none exists, it fails closed without staging the component.
- The public desired-state manifest is signed by the base trust root and binds every component plus the required base contract. Downloads are commit-scoped immutable objects and are verified by URL scope, size, SHA-256, signature, manifest identity, and package identity before staging.
- An official update stages a complete candidate Profile generation on the same volume, preserves the third-party overlay, and changes no active bytes. The explicit Agent request is the first confirmation and authorizes only signed metadata/manifest inspection. A separate native confirmation displays the exact delta; only then may component payloads be downloaded, reverified, staged, and followed by an orderly automatic restart. Activation is one atomic generation switch and becomes committed only after the existing renderer-health boundary. Failed activation restores and reopens the last-known-good generation. Background prompt deduplication is keyed by the existing update state's `(current generation, target generation)` pair, so a rollback to bundled or another generation offers the same signed recovery target once again without repeatedly prompting when both identities are unchanged. The application never downloads component payloads or restarts without that native confirmation.
- Local, dirty, unpackaged, temporary, Computer Use and loopback candidates are never production update inputs. They use isolated user-data/DSH homes plus loopback or fixture metadata, hold no production signing/R2/Feed/desired-state write authority, and cannot upload or activate public Desktop/Profile/component/update bytes. Production accepts only the exact protected-main CI artifact set whose source/run/target/bytes/hash/signature and install/update receipts all match the frozen candidate; a local path, copied bundle, symlink, dev signature, fixture receipt or rebuilt byte fails closed before the first production write.
- Plugin-only admission is allowed only when the repository impact classifier proves that all changed production inputs belong to independently packaged compatible components and that no shared input changed. The lane builds, tests, composes, and publishes only those components plus the final desired-state manifest. It must not build, relabel, upload, or revalidate Desktop installers or unrelated components.
- The accepted Base SDK is a content-addressed, manifest-verified artifact of the pinned Harness ABI, its clean-source build receipt and emitted `lib` bytes, the Desktop runtime/client carrier, and non-component Profile inputs. The Base lane builds Harness once; Desktop deterministically materializes those exact emitted libraries into its Yarn-installed packages and applies only the admitted e-Mate overlays, so Electron never falls back to the registry rc.7 implementation for a changed package. Platform jobs restore that same SDK and may not rebuild Harness. Cross-workflow Profile bootstrap must download it by the explicit `ci_run_id` and tested source SHA. Actions cache is only a same-CI performance optimization and is never release evidence. A missing or invalid SDK, tracked or untracked Harness source drift, receipt mismatch, unadmitted overlay, or resolved-package hash mismatch fails closed. Each changed component owns a frozen `pnpm-lock.yaml`, is installed outside the root workspace from that lock, and carries the lock plus its signed runtime closure in the component payload. Only the fixed Base ABI imports declared by the component contract may resolve from the Base SDK.
- Before a changed component can be published, CI merges its immutable payload with the complete currently accepted component set independently for `darwin-arm64`, `darwin-x64`, and `win32-x64` and materializes every referenced byte. When all changed payloads are portable, one macOS runner verifies all three target closures and boots the shared real Cordis Host/Web Loader graph once on arm64; unchanged platform components retain their already accepted native execution receipts. A changed target-bound component instead keeps the matching native runner and complete-generation boot for every affected target. Candidate artifacts retain only signed composition metadata; the temporary full store is verification state and is not forwarded as a release payload.
- The release workflow accepts only already successful CI evidence for the exact classified lane. A protected squash merge may promote the same immutable pull-request artifacts only when GitHub reports that exact PR merged into the current `main`, the current commit has the PR base as its sole parent, and the tested PR tree SHA equals the current `main` tree SHA. The release receipt keeps both the tested source commit and rewritten `main` commit. Any other merge shape or tree drift must run `main` CI. Normal plugin publication performs no build or test: it production-signs the admitted payload, uploads only missing immutable changed objects, performs authenticated and public size/SHA-256 readback, rechecks the parent desired state, then replaces the target's single `no-store` desired-state object. The one-time 2.0.11 bootstrap may build all accepted component targets from the already accepted Base SDK and must pass the same three complete-generation boots; it still does not build an installer.
- Therefore a source/test change inside one compatible portable component normally runs that component's build/test plus one three-target materialization and one shared-graph boot, then publishes only that component delta. A test-only change emits no release bytes. A target-bound component keeps its native target matrix. DMG/EXE, npm carrier clean-install and native Base acceptance rerun only when the classifier selects the Base lane or an explicit formal carrier release is dispatched; workflow or version labels cannot force a component change into or out of that lane.
- Changes to the pinned Harness pointer/source, Desktop runtime/API/updater, Electron or native helpers, permissions, shared Profile/core layer, the root or Desktop dependency locks, packaging/signing inputs, component format/trust rules, or an incompatible component contract enter the Base lane. A component's own dependency lock remains that component's input and may use the plugin lane. Unknown paths and incomplete provenance enter Base; there is no permissive fallback.
- CI and release workflows consume the same checked-in classifier result and finish through one aggregate required check. A workflow-local path list, manually selected faster lane, or version label cannot override the classifier.

- Import only authoritative, non-deleted old e-Mate/ECoreX sessions; preserve sources unchanged and make import idempotent. These roots are optional read-only sources, never a startup or current-Session dependency: missing, removed, temporarily unreadable or discovery-raced sources degrade to a clean no-op with at most one redacted Host-lifecycle diagnostic and no sidebar/Session error projection, while integrity, identity and target-persistence failures continue to fail closed.
- User data stays under the resolved `$DSH_HOME`; npm installation directories are read-only code/resources.
- Supported release platforms are macOS 13+ arm64/x64 and Windows 10/11 x64.
- Keep the existing download, admin, audit, and public R2 origins unchanged. Published Desktop installers and Profile components use version-and-commit-scoped immutable keys; all prior objects remain frozen and are never overwritten, and the application server must not become the binary origin.
- A Base release requires clean native installation on every selected platform, automated closure checks, startup/performance evidence, and Computer Use acceptance. A plugin-only release instead requires the changed component tests, composition with the accepted Base/Profile generation, restart/health/rollback proof, and immutable public receipt; it must not rerun unrelated native installer acceptance.
